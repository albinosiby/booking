# Firebase booking notifications — proposed design

Status: design approved on 23 October 2026; implementation and local validation completed. Hosted migration, secrets and deployment remain user-operated. See [the deployment guide](firebase-notifications.md) for the implementation handoff.

## Product analysis

Owners and authorized staff need device notifications when an ordinary booking is placed, cancelled, or rescheduled, including bookings placed through the public website and supported voice workflows. The user confirmed that “supervise” means a Supabase Edge Function and that recipients are the owner and authorized staff.

Core scope: register each signed-in device, refresh its FCM token, unlink it on logout, select recipients using existing permissions and assignments, send the three booking events, show foreground/background notifications, and open the relevant booking when tapped. Multiple devices per account are supported.

Assumptions: staff must have `manage_bookings` and assignment to the affected business/resource; owners receive all three events in their organization. Include the acting user if eligible. Start with Android and iOS configuration; iOS delivery depends on Apple/Firebase provisioning. Web push, customer notifications, preferences, and an inbox are optional follow-ups. Admission/coaching sessions stored in `bookings` are excluded from ordinary order notifications to prevent bulk session alerts.

Competitor analysis is not needed for this incremental infrastructure feature; it follows the application's existing booking and access workflows.

Risks: missing credentials or denied OS permission prevent delivery; stale tokens and removed staff must be excluded; retrying an uncertain FCM response can cause duplicates; push delivery depends on OS/provider conditions. Queue processing must not slow down order transactions.

## Existing implementation findings

- Flutter uses Supabase authentication by default. `lib/main.dart` initializes Firebase only in the alternate Firebase-auth branch.
- `firebase_core` and `firebase_auth` exist, but `firebase_messaging` is absent from this checkout's `pubspec.yaml`.
- Android has `google-services.json`; its package must continue matching `bookingservice.tatos.tech`.
- No iOS `GoogleService-Info.plist`, push entitlement file, or push background-mode configuration was found.
- The app calls the Supabase `booking-api` Edge Function. Its shared source lives under `backend/src` and `backend/edge`; the checked-in Edge entrypoint is generated by `npm run edge:build`.
- Cloud tables use the private `booking_app` schema and a restricted server database connection. Device tokens should follow that boundary.
- Booking creation, rescheduling and cancellation write `booking_history` in their existing transaction. Website creation also writes the history record.
- Deployed Edge Functions could not be inspected: the Supabase connector returned a permission error. No existing remote sender was verified.
- There are pre-existing authentication/platform edits; implementation must preserve them.

## System architecture

Flow: authenticated app → device-registration API → private device table. Successful booking transaction → durable notification event → authenticated dispatcher Edge Function → FCM HTTP v1 → eligible devices.

Keep Supabase Auth as the identity authority. Initialize Firebase Messaging independently of the selected auth provider. An FCM token identifies an app installation; it is never accepted as proof of account identity.

Add a dedicated sender Edge Function with a clear notification name, rather than assuming a function literally named `supervise` exists. It accepts only authenticated internal dispatch requests. A scheduled invocation drains pending work in bounded batches; an optional post-commit wake-up reduces latency. The durable queue remains the recovery mechanism if that wake-up fails. The schedule is part of the explicit deployment handoff, not a Codex recurring automation.

Enqueue from the three shared booking transaction paths, using the new booking-history ID as the event key; include the public website creation path. This captures explicit rescheduling even if only the selected resource changes. Do not infer rescheduling from payment/version updates. Do not call FCM inside a database transaction.

Use the existing restricted database connection for private tables and only the specific additional grants required by the new operations. Keep Firebase service-account credentials in server secrets. Use short-lived Google OAuth credentials for FCM HTTP v1, with an expiry-aware access-token cache.

Workers claim bounded batches using leases and `FOR UPDATE SKIP LOCKED`, release database transactions before network sends, and retry transient errors with bounded exponential backoff. Resolve recipient eligibility at dispatch and recheck it on retry. Permission changes cannot retract a message already handed to FCM.

## Database design

Proposed tables in `booking_app`:

| Table | Purpose and key fields |
| --- | --- |
| `notification_devices` | Installation ID, authenticated user ID, FCM token, platform, enabled state, created/updated/last-seen timestamps. Unique installation ID and unique token. |
| `booking_notification_events` | Event ID, unique history ID, booking/organization/business/resource IDs, event type, minimal event snapshot, queue state, lease and retry timestamps. |
| `notification_deliveries` | Event and device IDs, token generation/version, attempt count, state, next attempt, lease expiry, sanitized last error, FCM acceptance timestamp. Unique event/device pair. |

Index active devices by user ID; index pending events/deliveries by state and next-attempt timestamp. Use foreign keys for events and delivery relationships and check constraints for event/platform/state values and retry bounds. Match the existing text user-ID type; exclude service actors such as voice-agent identities from device recipients.

Keep tables outside exposed Data API schemas, deny direct client access, and enable RLS as defense in depth with narrowly scoped server grants. Device registration derives the user ID from the verified session. A per-installation secret stored in secure device storage proves ownership for rebinding an installation after account switching; never trust a client-supplied user ID or installation UUID alone. Tokens and installation secrets are excluded from logs and API responses.

Upsert replaces the installation's old token; token rotation preserves its device identity. Logout disables registration before credentials are cleared and deletes/rotates the local FCM token. A failed online unlink must leave a pending cleanup marker and avoid silent reuse on another account. Retry cleanup on reconnection; offline logout cannot guarantee immediate revocation of a server-side push target. Rebinding must be atomic, and stale asynchronous registration callbacks must not reattach a previous user.

Only explicit provider errors identifying an unregistered token disable that token, guarded by its stored version so an old failure cannot disable a newly refreshed token. Generic payload or credential errors must not delete tokens.

Migration ownership remains with the user. Implementation will prepare migration files using the repository's migration conventions, with prerequisites, exact apply steps, validation queries, required role grants, schedule setup, and rollback/recovery instructions. No live schema changes are authorized.

## API design

Use the existing authenticated API transport and error format:

| Operation | Authentication | Result |
| --- | --- | --- |
| `POST /v1/notifications/devices` | Current user session plus installation proof when replacing/rebinding | Idempotent registration/token refresh, returning only device ID and status. |
| `POST /v1/notifications/devices/:id/unregister` | Current user must own registration | Idempotent disable for logout or revoked permission. |
| Sender Edge Function | Dedicated internal secret; no public user dispatch endpoint | Claim pending queue work and return aggregate counts. |

Registration request: installation ID, platform, FCM token and installation proof; the server supplies account identity. Example success: `{ "id": "<device-id>", "registered": true }`.

Validate sizes and allowed platforms, apply existing rate limits, use no-store responses, and map invalid requests, missing authentication, ownership failures and server failures to the existing structured API errors. Notification failures do not invalidate a successful login or booking.

Sender input specifies only a bounded dispatch batch, never arbitrary tokens, user IDs, titles or message bodies. Resolve recipient membership, permissions and assignment from authoritative tables. Never expose the sender secret to Flutter or the website.

## Frontend design

No new screen is required. A feature-scoped notification Cubit coordinates authentication, permission, registration, incoming messages and taps through repository interfaces; Firebase and REST adapters stay behind those interfaces and are registered in GetIt.

After login or restored session, request OS permission in context and register the current installation when token acquisition succeeds. Listen for token refresh, retry transient registration on resume/reconnection, handle permission changes, and serialize account transitions. Notification setup failure must leave login usable and observable through sanitized diagnostics.

On Android, configure runtime permission, a high-importance booking channel, a monochrome notification icon and foreground presentation. On iOS, configure Firebase, push entitlements/background modes and foreground presentation, and wait for an APNs token before FCM token operations. Background notification payloads use OS presentation; avoid displaying them twice through a local handler.

Payload contains an event ID, booking ID and event type with concise display text. Avoid customer phone numbers, payment details, or other sensitive lock-screen content. Tapping opens booking details through existing GoRouter routes after auth/workspace restoration and a fresh server access check. Drop unauthorized or obsolete pending navigation when the account changes.

1. Prepare schema migration and private API device lifecycle; add ownership/isolation tests.
2. Add transactional event enqueueing and a shared sender service with the dedicated Edge entrypoint.
3. Add Flutter Messaging lifecycle, native platform configuration, presentation and tap handling.
4. Verify integration, regenerate the existing Edge API artifact, and document deployment and manual acceptance checks.

This is one feature increment. A working estimate is 2–3 engineering days including review and device acceptance, assuming signing, Apple provisioning, Firebase access and database deployment access are ready. No wider redesign is required.

## Security

Verify Supabase sessions through the existing backend. Select only active owner/staff memberships in the same organization; staff additionally need booking-management permission and matching business/resource assignment. On reschedule, use the current resource for notification eligibility and do not disclose prior resource details to newly eligible staff.

Protect installation rebinding, redact tokens/secrets, use HTTPS, retain restricted schema access, and restrict sender execution to server callers. A payload booking ID is only a navigation hint, never authorization. Minimize payloads and queue retention; periodically prune old successful deliveries and stale devices under a documented retention policy.

## Testing

- Backend integration: all three event types; app, website and voice booking paths; rolled-back transactions enqueue nothing; repeated command keys enqueue once; payments and check-in enqueue nothing; admission sessions excluded.
- Recipient isolation: another organization, unassigned business/resource, removed staff and revoked permission receive nothing. Eligible owner/staff devices receive the event, including multiple devices for one account.
- Device lifecycle: initial registration, restored login, token rotation, logout, account switching, concurrent callbacks, denied/revoked permission and failed cleanup recovery.
- Sender: partial success, explicit unregistered token, transient provider failure, invalid credentials/payload, retry exhaustion, concurrent workers, expired leases, and refreshed-token races.
- Flutter: lifecycle/Cubit tests, notification tap during cold start and login, authenticated route access, and no double foreground display.
- Run formatting, Flutter analysis and focused tests, backend build/tests and Edge type/build checks. Verify Android build and iOS configuration where the available toolchain permits.
- Physical-device acceptance after deployment: place, cancel and reschedule a booking while the app is foregrounded, backgrounded and normally terminated. Verify an unauthorized second account/device receives nothing. OS force-stop restrictions are documented.

## DevOps and documentation

Prerequisites: enable FCM HTTP v1 for the Firebase project, provision a least-privilege sender service account, install its credentials as Supabase secrets, verify Android project/package mapping, and provide the iOS Firebase config plus APNs key/team/signing setup. Never paste private keys into chat, source control or client build arguments. Web push would additionally require web Firebase options, VAPID configuration and a service worker.

Deployment order: user applies/validates the migration → configure server secrets → deploy API and sender → enable the authenticated dispatch schedule → publish the configured app → complete two-account/device acceptance. Until the full chain is deployed, actual device delivery is unverified.

Monitor pending queue age, retry/dead-letter counts, FCM acceptance/error counts and invalidated registrations with event/request IDs only. FCM acceptance is not proof that a device displayed a notification. Delivery is at-least-once; stable event IDs reduce duplicates but cannot guarantee exactly-once OS presentation after an uncertain network response.

Recovery: pause dispatch and enqueueing with server feature flags, preserve queue state, revert application/function versions as needed, and resume only after checking pending-event age and recipient permissions. Drain or explicitly discard retained work before removing new tables; schema rollback is user-operated. Use existing database backup procedures and document any plan-specific prerequisites.

Implementation documentation will include setup/secrets, migration application and validation SQL, schedule invocation, deploy/rebuild commands, troubleshooting, rollback, API contracts and a short user guide covering permission and notification taps. Existing CI should run the new focused tests and existing required checks.
