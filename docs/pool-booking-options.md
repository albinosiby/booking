# Pool options in New booking

Select a swimming pool business and pool space in New booking. **Space → Booking option** contains Regular admission, configured Group offers, Swimming plan and Coaching in one vertical list. Every choice is a full-width elevated button; the selected choice has the primary green background and a checkmark. There is no separate Single visit button or row of pool mode chips. Group offers retain their configured name and group-size explanation beneath the button label, so multiple offers remain distinguishable. Only configured regular/group options appear. Plan/coaching choices retain the existing missing-plan empty state. Rescheduling shows only the existing booking choices, without plan/coaching purchase buttons.

Regular admission and Group offer keep the current start/end grid, pricing, discount and split-payment flow. Swimming plan and Coaching replace only section 3 (Date & time) with shared admission schedule fields, scoped to the selected business/pool and plan kind. Customer, Space (including all booking-option buttons) and Payments remain in the same New booking layout, including while reviewing an admission. The selected customer and date carry over. Swimming visit duration starts at the pool’s configured minimum and can be extended in 30-minute steps. Coaching keeps the plan’s fixed class duration. Coaching shows the assigned coach read-only. Review displays allowance, expiry and payment information before Confirm admission.

Switching preserves the customer and pool. If schedule, plan or payment entries would be discarded, a confirmation is required. Cancel keeps the current form. The same business and space selectors remain available. Changing pool reloads that pool’s plans; leaving a pool business returns to the regular booking flow. Selecting Regular admission or Group offer from a plan/coaching form first uses the same discard confirmation, then selects the exact requested booking option; cancellation leaves the plan and payments intact. Missing plans show an empty state and owners can open Configure plans. Switching is disabled during loading, confirmation or an uncertain saved result; the existing retry flow verifies that same command.

Models own the selected pool option and filtered plan choices. BookingFormCubit coordinates single visits; AdmissionCubit and the existing admission repository own plan previews and creation. Shared AdmissionScheduleFields, AdmissionPaymentFields and AdmissionReviewSummary widgets are reused by New booking and the standalone New admission/renewal page. Plan validity metadata maps through the repository to calculate the displayed expiry from the activation date using calendar month/year clamping, then the server preview confirms it. No separate booking is created when an admission is purchased; fixed admission sessions continue to follow the existing admission backend rules.

No new migration or backend deployment is needed for this UI change. The previously prepared/deployed admissions API and its database migration must already be available. Reload the updated Flutter source to test. No APK was built and no phone installation, deployment or live migration was performed.

## Flow audit fixes

The admission form now uses the same cached bank account and space-to-bank routing catalog as Single visit. UPI/card/bank payments show the mapped/primary bank and allow another receiving account to be selected. The form shows the split-payment total and remaining balance, offers Pay balance, and rejects invalid amounts and overpayments before review. Authoritative preview totals are checked again in case the plan price changed.

Definitive confirmation rejection clears the old preview and requires a new review. Unknown network results keep the original command and locked draft for retry; a saved admission cannot be submitted again. Option switching also guards loading and an already-open discard prompt. Admission time input uses the shared 24-hour picker.

These are app/repository changes using existing APIs. No new migration or API deployment is required. Local automated checks cover all three flows, unpaid/partial/full split payments, bank routing and account overrides, switching/cancel-discard, stale preview recovery, idempotent retry and light/dark narrow-screen rendering. Backend regression checks run against an isolated in-memory database, not the live project.

The admission footer uses Review admission / Confirm admission / Retry confirmation in place of booking actions. Flexible attendance hides weekday/start-time controls; fixed attendance reveals them. Expiry is read-only and follows the selected plan’s configured validity. No new migration or API deployment is needed for this layout change.

## Loading optimization

Pool plan metadata is warmed after the priority booking reads using the existing two-worker background queue, only for authorized users with an activated pool. This warm-up loads metadata only; it does not fetch previews, reservations, invoices or reports. Adjacent Swimming plan/Coaching switches reuse the already authorized typed catalog for up to 20 seconds, preserving its original fetch timestamp and avoiding a fresh loading frame. Expired/denied catalog state is not reused. Availability, preview and final confirmation remain server-validated. No API deployment, migration or APK build is required.

## Agreed plan and coaching amount

In New booking → Swimming plan/Coaching → Payments, authorized collectors can edit **Plan amount** before review. It starts at the configured fee. Entering 2300 for a configured 2500 plan sets the final payable fee to 2300; collecting 2300 leaves no balance. There is no separate discount control. Collect full, half, other amount, split payments, Pay balance, review totals and outstanding balances use that agreed fee. A 1000 collection against a 2300 fee leaves 1300 due. Existing payment entries are not silently rewritten if the fee is reduced; overpayments must be corrected before review.

The field accepts amounts from zero through 1,000,000 currency units with at most two decimal places. Blank, negative, nonnumeric, over-precision and out-of-range entries cannot reach review. A new plan or space resets the override to its configured fee. Customer/date edits retain the agreed fee. Review and uncertain confirmation lock fee editing along with the other command data; use Edit admission details before changing a reviewed amount. Staff without payment-collection permission retain configured pricing and cannot submit an override.

The API accepts optional integer `plan_amount_minor` on `/v1/admissions/preview` and `/v1/admissions`. Omitting it preserves configured pricing for existing clients. Preview and final creation independently verify current owner/collection permissions and business/space scope. The requested amount is bound into the preview token and idempotent command. `admissions.total_minor` saves the agreed fee, while the existing JSON plan snapshot stores `configured_price_minor` and the charged `price_minor`; creation/renewal audit details retain both configured and agreed amounts. Payment collection limits and refunds continue to use actual balances and recorded receipts. The configured business plan price is not changed.

No SQL migration is required. Release the rebuilt booking-api before the client so it accepts the optional amount field. The field is shown in the New booking flow; standalone admission forms keep their existing UI. Test with full, partial, unpaid, zero-fee and split collections, invalid amounts, changed permissions and modified preview/command payloads. No test admission or financial transaction should be created in the live database for release checks.
